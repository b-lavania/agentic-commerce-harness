Agentic commerce harness

If an agent is going to buy a laptop and put it on an invoice, someone has to check two things: did it pick the SKU the buyer actually asked for, and did it bill inside the authority it was given. This repo is that check. It does not move money.

v0.1 is a Python package you can clone. Fifteen scenarios, two in-process sims, a curriculum that stops once the invoice is sent. Run ./scripts/test.sh.

Why this exists

Two questions, one written mandate

Most “agentic commerce” talk collapses shopping and checkout into one demo. That is the wrong unit. An agent can already change which product a buyer sees, and it can already write a bill. Those are different failure modes. One is a bad SKU. The other is a bill nobody authorized. Mixing them into a single “the agent bought it” score hides both.

ACES (summarized in MBI) showed that shopping agents are not small humans. They miss a cheaper identical listing. They favor a rank that depends on the model, even when the catalog is just JSON. They react to sponsored tags and platform “picks.” A seller rewrite of the description can move share. Upgrade the model and the modal product jumps. If you grade “did something get shortlisted,” a first-hit policy looks fine.

Ping’s 2027 retail piece is the other half. People will let an agent search and compare long before they let it pay. They want caps, an approval step, and a way to undo. The retailer still has to know whom the agent represents, what it may do, and how to reconstruct the action later. Checkout without that is not agency. It is an unsigned payment.

ACES
Did it pick the right SKU?

Under rank, blurb, and dominance bias. Two legal laptops that both have a spare is not a pass if the buyer asked for the cheaper one.

Ping
Did it stay inside the mandate?

Authoritative catalog and price book, preview before send, credit memo instead of rewriting a sent invoice, an audit trail. Checkout stays off until that holds.

Grade
The buyer’s written task

Pass or fail comes from the scenario, not from which model ran. The same mandate should fail GPT, Claude, and a gold script for the same reason.

That is why the harness splits a commerce agent from a payments agent, and why settlement stays outside this cert. You can certify a quote and a bill without standing up Stripe. You cannot certify a checkout if the quote was already wrong. The catalog spike found no shared SKU with Counter, so the dashed arrow stays empty.

What v0.1 actually is

Green tests replay a script

Be honest about the current cert. The runner walks steps[] from a JSON file. If those steps match the sim, the scenario passes. That is useful as a regression suite. It is not proof that an agent would have chosen those tools. There is no model client here, and no MCP server.

The script is graded, not just replayed. Each step can carry expect. attach_addon refuses a service whose family was not selected. h1_reject_incompatible_addon calls that tool on Marketlane-only care and the refusal is the pass. return_to_draft is a real tool. A missing price-book row fails the quote. rate_usage rates a batch and stops; the agent attaches the usage line itself.

JSONL export is real: hashes, milestones, forbidden hits. Treat it as the start of an audit log, not a training set.

Two agents

The quote crosses. The dollars stay put.

Commerce searches, filters, compares, and saves a shortlist. Payments loads that shortlist, attaches lines from the price book, previews, and sends. What moves between them is sku, quantity, and line type. No cents. The three Counter fields on the handoff stay empty on purpose.

compose_quote writes those lines: an appliance becomes setup plus recurring, a service becomes recurring, and a missing price-book row fails the run. The picture below is that contract. Counter fields stay empty. The catalog spike said not to invent a cafe SKU to fill them.

Rank and seller copy stay on the commerce side. They are not part of the handoff.

Horizons

One tool call counts. A reasoning turn does not.

H1 is discovery through a shortlist that passes the compatibility oracle. H2 is the invoice machine through sent, with recon on usage. H3 is Counter checkout, documented only; see ADR 001. Neither sim accepts set_amount, rewrite_sent, checkout, or create_payment.

Oracle and invoice rules already in the spec
Oracle Shortlist of 1–4. Appliances have to match the buyer’s deployment, perf, spare, os, license, and certs. A service only stays if its compatible_with hits a shortlisted appliance family. Compare tables drop marketing copy. If search returned nothing, the agent has to refine before it saves.
Invoice Draft, generated, sent. After sent, the only legal correction is a credit memo onto the next invoice. Usage needs partner, SMB, and subscription ids. Preview will not promote to generated if rated cents and invoice cents disagree.
Money

The agent can look at cents. It cannot type them.

attach_line already rejects an agent-supplied amount. The price book is the only writer of unit prices (USD on the book; the handoff currency field stays empty so Counter can own payment currency later). Line types are setup, recurring, and usage. Usage does not belong on a discovery quote.

If usage is on the invoice, send is blocked until unexplained variance is zero. A credit memo is a new document that points at the sent id. Editing the sent invoice in place is the illegal tool rewrite_sent.

Invoice machine

  draft ──preview──▶ generated ──send──▶ sent ──memo──▶ credit_memo ──▶ next_invoice
    ▲                    │                  │
    └── return_to_draft ─┘                  │ rewrite_sent
                                            ▼
                                         refused

  sent is immutable. later usage lands on next_invoice.

return_to_draft moves generated back to draft and clears the preview milestone. Editing a line while the invoice is generated is refused until that return.

Worked example

Office laptop through a sent invoice

Search for a standard office laptop with a spare, set on-prem facets, compare three machines on the whitelist attributes (not the marketing line), attach desk care, save the shortlist, then commit the Northline 14 plus care. compose_quote emits three lines with no cents. Payments attaches them, preview shows the ledger, send flips the state to sent. Counter ids stay null.

Replay that path with ach-driver --view out.html. Commerce shows the hits. Handoff shows sku, qty, and line type. Payments shows $2,070 only after preview.

Next

Checkout stays on the other side of the handoff

The cert above is in the tree: step expects, a real incompatible-addon refusal, quote composition, fail-closed prices, the invoice machine, preference and position scenarios, a recurring cap, and the trace page. The Counter spike stopped the bridge. Cafe SKUs and workspace-computer SKUs do not meet, so there is no ADR 002.
